# v0.7.1 — Standardized & Advanced Testing

Adds the testing layers that should be in any production-grade auth server: SLA assertions, soak / spike / fuzz, security, race detection, coverage.

**Last run:** 2026-05-31
**Real bug found:** `password.Verify` panicked on the input `("0", "$$$$$")` due to empty `expectedHash` causing `keyLength=0` in argon2. Fixed in [internal/shared/password/password.go](auth-server/internal/shared/password/password.go); fuzz now passes 44k+ executions with zero failures.

## Full test pyramid

| Layer | Tool | What it answers |
|---|---|---|
| **Unit** | `go test` | Does this function do the right thing on every meaningful input? |
| **Fuzz** | `go test -fuzz` | Are there inputs the developer didn't think of that crash / mis-verify? |
| **Race** | `go test -race` | Do any code paths share state without locks? |
| **Smoke** | `bash + curl` | Is every endpoint wired and returning the right status? |
| **Integration** | `go test` over HTTP | Do multi-step real flows work? |
| **Security** | `go test` over HTTP | Are common attack classes refused? |
| **Stress + SLA** | Custom Go binary | Does the system meet its latency budget under load? |
| **Spike** | Custom Go binary | What happens under a 10× burst? Does it recover? |
| **Soak** | Custom Go binary | Does latency drift or memory grow over a long run? |
| **A/B** | Custom Go binary | Which of two implementations is statistically faster? |
| **Coverage** | `go tool cover` | Which lines of code aren't exercised by tests? |

## 1. SLA assertions

The stress binary accepts budget flags. Any non-zero budget that is breached causes exit status 2, which fails CI.

```bash
go run ./test/stress \
    -scenario jwt-verify \
    -concurrency 50 -duration 30s \
    -sla-p95 20ms -sla-p99 50ms \
    -sla-fail-pct 0.1 -sla-min-rps 5000
```

| Flag | Meaning | Default |
|---|---|---|
| `-sla-p95 DUR` | fail if p95 > DUR | off |
| `-sla-p99 DUR` | fail if p99 > DUR | off |
| `-sla-fail-pct PCT` | fail if failure rate > PCT% | off (default 1% threshold applies if no SLA given) |
| `-sla-min-rps RPS` | fail if throughput < RPS | off |

### Verified

**Passing run** (`jwt-verify` 50w × 10s with budgets p95 ≤ 20ms, p99 ≤ 50ms, fail ≤ 1%):

```
throughput:  10995 req/s
p95: 5.82ms   p99: 8.25ms   fail: 0%      ← all under budget
exit 0
```

**Breach run** (`login` with deliberately-tight p99 ≤ 1ms):

```
SLA BREACH
  - p99 12.27s > budget 1ms
exit 2
```

The asserting flag works in both directions: pass when budgets are met, fail loudly with the actual values when not.

### Suggested SLAs for production (v0.8.0 onwards)

| Endpoint | Path | p95 budget | p99 budget | Notes |
|---|---|---:|---:|---|
| Stateless auth | `/me` Bearer | 20 ms | 50 ms | After Redis Principal cache lands, target 5/10ms |
| Refresh | `POST /refresh` | 50 ms | 100 ms | Single DB write + JWT sign |
| Login | `POST /login` | 250 ms | 400 ms | Argon2id 64MB×3 is the floor |
| JWKS | `GET /.well-known/jwks.json` | 10 ms | 25 ms | Add CDN max-age=3600 to drop p99 to LB level |
| OAuth token | `POST /oauth/token` | 100 ms | 200 ms | Code grant: Redis read + DB write |

## 2. Soak test (endurance)

`go run ./test/soak -duration 1h -concurrency 50 -bucket 1m -sla-drift-pct 50`

Per-bucket output: count, p50/p95/p99, failure %, current heap size. After the run, computes p99 drift between first and last bucket. If `-sla-drift-pct` is set and drift exceeds it, exits 2.

### Verified (60s × 30 workers, bucket=10s, `/me` JWT path)

```
elapsed   count   p50       p95        p99        fail%   heap
10s       112697  2.56ms    3.62ms     4.73ms     0.00    2.3MB
20s       113610  2.54ms    3.57ms     4.50ms     0.00    4.0MB
30s       112414  2.59ms    3.54ms     4.26ms     0.00    5.0MB
40s       110772  2.57ms    3.71ms     5.15ms     0.00    8.1MB
50s       110521  2.60ms    3.72ms     4.90ms     0.00   11.1MB
1m0s      110864  2.59ms    3.75ms     4.90ms     0.00    9.7MB

Summary
  total ok:   670,878
```

- 670k+ requests across 60s with **zero failures**.
- p99 drift +3.9% well under any reasonable budget.
- Heap grew to ~11 MB then dropped to 9.7 MB → GC working, **no leak signature**.

## 3. Spike test

`go run ./test/spike -baseline 10 -burst 100 -baseline-duration 5s -burst-duration 5s -recovery-duration 10s`

Three phases reported separately:

### Verified (10 → 110 → 10 workers)

```
baseline   n=51,316  p50=914µs   p95=1.45ms   p99=1.83ms    max=7.2ms    fail=0%
burst      n=52,648  p50=9.99ms  p95=14.26ms  p99=17.48ms   max=49.7ms   fail=0%
recovery   n=98,056  p50=943µs   p95=1.54ms   p99=2.25ms    max=14.3ms   fail=0%
```

- 11× concurrency jump: p99 went from 1.8 ms → 17.5 ms (10×) — predictable queuing.
- Zero failures during the burst.
- p99 fully recovered within seconds (1.83 → 2.25 ms is essentially noise).

### SLA flags

| Flag | Meaning |
|---|---|
| `-sla-burst-fail-pct PCT` | fail if burst-phase failure rate > PCT% (default 5%) |
| `-sla-recovery-p99 DUR` | fail if recovery-phase p99 > DUR |

## 4. Fuzz tests

Go's native fuzzing (`testing.F`, Go ≥ 1.18). Each fuzz test seeds a corpus plus runs random mutations.

| Target | File | What it checks |
|---|---|---|
| `FuzzVerifyPKCE` | `internal/oauth/app/pkce_fuzz_test.go` | No input pair returns `true` unless `BASE64URL(SHA256(verifier)) == challenge` |
| `FuzzSplitScopes` | `internal/oauth/app/pkce_fuzz_test.go` | No empty tokens are ever returned |
| `FuzzJWT_Verify` | `internal/token/app/jwt_fuzz_test.go` | Any nil error must come with non-empty claims (no spurious accepts) |
| `FuzzJWT_RejectsAlgNone` | `internal/token/app/jwt_fuzz_test.go` | `alg=none` JWT must always fail Verify (CVE class) |
| `FuzzVerify_NoPanic` | `internal/shared/password/password_fuzz_test.go` | `password.Verify` never panics on any string input |

### Run

```bash
# Smoke (5s each): catches obvious bugs in CI
go test ./internal/oauth/app/      -run="^$" -fuzz=FuzzVerifyPKCE     -fuzztime=5s
go test ./internal/oauth/app/      -run="^$" -fuzz=FuzzSplitScopes    -fuzztime=5s
go test ./internal/token/app/      -run="^$" -fuzz=FuzzJWT_Verify     -fuzztime=5s
go test ./internal/token/app/      -run="^$" -fuzz=FuzzJWT_RejectsAlgNone -fuzztime=3s
go test ./internal/shared/password/ -run="^$" -fuzz=FuzzVerify_NoPanic -fuzztime=5s

# Deep (overnight): much higher chance of finding edge cases
go test ./internal/shared/password/ -run="^$" -fuzz=FuzzVerify_NoPanic -fuzztime=8h
```

### Results

| Fuzz | Executions in 5s | New corpus entries | Verdict |
|---|---:|---:|---|
| `FuzzVerifyPKCE` | 758,524 | 3 | ✅ pass — no false-true |
| `FuzzSplitScopes` | 333,949 | 49 | ✅ pass — no empty tokens |
| `FuzzJWT_Verify` | 363,311 | 104 | ✅ pass — no spurious accepts |
| `FuzzJWT_RejectsAlgNone` | 190,655 | 2 | ✅ pass — alg=none always rejected |
| `FuzzVerify_NoPanic` (post-fix) | 44,629 | 11 | ✅ pass after fix |

### Bug found

Initial run of `FuzzVerify_NoPanic` crashed in **~3 seconds** with a `nil pointer dereference` inside `argon2.IDKey`. Saved input: `("0", "$$$$$")`. Root cause: when the encoded hash is `"$$$$$"`, `strings.Split` returns 6 empty segments, so `expectedHash` decoded to 0 bytes, and `argon2.IDKey(..., keyLength=0)` panicked inside `blake2b`. Fixed by adding an empty-salt/empty-hash guard in `password.go:69`. Test now passes 44k+ executions cleanly. The seed input is preserved at `internal/shared/password/testdata/fuzz/FuzzVerify_NoPanic/c6091420777c30e5` to permanently regression-test the fix.

## 6. Security tests

`go test ./test/security/... -count=1 -v`

10 tests covering common attack classes. All pass; two tests log **known gaps** that we explicitly target in the v0.8.0 Security Hardening phase.

| # | Test | Class | Result |
|---|---|---|---|
| 1 | `TestSec_JWT_AlgNoneRejected` | JWT `alg=none` attack (CVE-2015-9235 family) | ✅ rejected with 401 |
| 2 | `TestSec_JWT_TamperedPayloadRejected` | Modify JWT payload byte → must fail signature | ✅ rejected with 401 |
| 3 | `TestSec_JWT_GarbageRejected` | Empty / malformed / 100k-char Bearer | ✅ all return 401 |
| 4 | `TestSec_SQLi_LoginEmail` | 6 classic SQLi payloads in login email | ✅ none login, none 500 |
| 5 | `TestSec_SQLi_RegisterTenantName` | SQLi in tenant_name on register | ✅ stored literally; health OK after |
| 6 | `TestSec_BruteForce_NotRateLimited` | 20 wrong-password attempts in a row | ⚠️ **KNOWN GAP**: all 20 returned 401 with no slowdown. Tracked for v0.8.0 |
| 7 | `TestSec_HeaderInjection_EmailField` | CRLF in email JSON value | ✅ no `X-Injected` in response |
| 8 | `TestSec_Timing_LoginConstantTime` | Compare login time real-user vs nonexistent-user | ⚠️ **KNOWN GAP**: real=95ms fake=1.5ms (ratio 62×) — leaks account existence. Tracked for v0.8.0 |
| 9 | `TestSec_CORS_DoesNotReflectArbitraryOrigin` | Hostile `Origin: https://evil.example.com` | ✅ does not reflect (current `*` is dev-only) |
| 10 | `TestSec_PKCE_PlainMethodRejected` | `code_challenge_method=plain` downgrade | ✅ never accepted |

### Known gaps for v0.8.0 (Security Hardening phase)

These are **documented**, not failures. The tests log them with `t.Logf` so they show up in CI output but don't break the build, and they'll flip to assertions when the gap is closed:

1. **No rate limiting** — implement per-IP + per-account counter in Redis; lock after 5 wrong attempts/min.
2. **Login timing leak** — even when the email is unknown, hash a dummy Argon2 to make timing constant.

## 7. Coverage

`./test/coverage.sh` — runs unit tests with `-coverpkg=./internal/...` against the whole internal tree, outputs `coverage/coverage.html`.

Current unit coverage is **7.7%** of `internal/`. This is the coverage from unit tests alone — the integration / smoke / security / stress suites run against the binary over HTTP and don't contribute to in-process counters. Real coverage including those would require building the server with `go build -cover -o iam-server` and a graceful SIGTERM handler that flushes counters on shutdown; that's tracked as a v0.8.0 task.

Unit-test coverage is most useful for pure-logic packages (`password`, `token`, `oauth/app`, `token/app`, `mfa/app`), all of which sit at high coverage individually. The 7.7% global figure is brought down by repo / handler / wiring code that doesn't have unit tests by design.
